# Capability 11: rpc

Status: **Draft — awaiting owner review.** Built to OpenVista's
[RPC-HTTPS contract](../../openvista/docs/RPC-HTTPS.md) (§1 client and
Janus, §2 Janus and em, §3 the reply rule), with the limits Em and the
owner settled on 2026-10-10.

`rpc` holds one stream per client session to a Unix socket a service
manager answers with one process per connection, and carries one
request's body to that stream and the one reply back, per HTTPS request.
The client speaks plain HTTPS (`POST`, HTTP/1.1 or 2); the backend speaks
a strictly request-and-reply byte protocol that keeps per-connection
state. Janus never interprets a request or a reply beyond the framing it
needs to find each one's end, and the one sign-on fact named below.

The first and only protocol is `xwb`, VistA's RPC Broker: OpenVista's
clients (CPRS through its workstation relay, and Rip's `xwb` package in a
browser) reach VistA on em, each session one em process running
`XWBP^%ZISTCPS`. Nothing outside the `xwb` framing rule and its sign-on
fact is specific to it.

```
 client ── HTTPS POST /rpc ──▶ janus ── Unix socket, one stream per session ──▶ em: XWBP^%ZISTCPS
        ◀── 200, the reply ──        PROXY line once, then each request body     (one process per stream)
```

## Scope and ownership

- Capability order: **11**, after webtransport.
- Surface: routes in exact-host site blocks; no global block.
- Cascade: **no**. A route belongs to the site that declares it; the
  global `janus` block takes no `rpc` and a global occurrence is a parse
  error.
- Default: **off**. Nothing exists until a site declares a route.
- Trust boundary: the backend authenticates the user (VistA's sign-on).
  Janus admits a request by host, path, method, content type, origin,
  size, and session token, caps sessions so unauthenticated clients cannot
  pile up backend processes, and passes the client's true address to the
  backend in the PROXY line. The target socket is trusted the way a
  registered upstream is; its mode admits only Janus's user.
- Exposure: no new listener. Routes are served by the site's existing
  HTTPS servers and obey the exposure mode with them.
- Dependencies: none beyond the standard library.

## Site Caddyfile grammar

```caddyfile
vista.example.org {
	janus {
		rpc /rpc unix//run/openvista/xwb.sock {
			protocol xwb            # the framing rule; the only legal value, and the default
			max_sessions 256        # sessions on this route, default 256, range 1–65535
			max_unsigned 16         # sessions not yet signed on, default 16, range 1–max_sessions
			per_client 16           # sessions from one client address, default 16, range 1–max_sessions
			per_client_unsigned 4   # not yet signed on, from one client address, default 4
			signon_timeout 60s      # end a session not signed on by then, default 60s, range 10s–10m
			rpc_timeout 10m         # one request's limit, request to reply's end, default 10m, range 10s–1h
			queue 8                 # requests waiting behind the running one, default 8, range 1–64
			max_request 1MiB        # request body, default 1 MiB, range 1 KiB–16 MiB
			max_reply 64MiB         # reply, default 64 MiB, range 1 MiB–1 GiB
			origin same             # browsers: default same; or one or more hostnames
		}
	}
}
```

`rpc <path> <target> [{ … }]` declares one route. The path is absolute,
exact (no prefix match), and unique within the site. The target is a
Caddy network address with network `unix` (`unix//run/openvista/xwb.sock`,
an absolute, clean path); any other network, a relative path, or a port is
refused, since the backend's one-process-per-connection model is a Unix
socket's. Each option appears at most once, an empty block takes every
default, and `per_client` and `per_client_unsigned` may not exceed
`max_sessions` and `max_unsigned`.

`origin` reuses the hub's token grammar and check, refusing `any`, as
webtransport does: a session cookie that any page could drive is a
cross-site request forgery surface.

The site's `janus` block must sit under exact host matchers only, as for
webtransport routes: a session's cookie is `__Host-`, bound to one host.
Wildcard and catch-all sites refuse the directive.

## Requests and responses

**`POST <path>`**, `Content-Type: application/x-xwb`. The body is exactly
one `xwb` message (RPC-HTTPS §3). The response, `200` with
`Content-Type: application/x-xwb` and `Cache-Control: no-store`, is the
backend's reply, byte for byte.

**Sessions and the token.**

- A request **without** a token must be a `TCPConnect` command. Janus
  admits the session (below), opens the stream, writes the PROXY line and
  the body, and returns the reply with the token, on this reply only:
  `Set-Cookie: __Host-ov=TOKEN; Secure; HttpOnly; SameSite=Strict; Path=/`.
  No other header carries it.
- The token is 32 bytes from `crypto/rand`, base64url without padding.
  Janus keeps only HMAC-SHA-256 of it under a per-process key (the auth
  store's pattern), so a memory image holds no usable token.
- Later requests present it as `Cookie: __Host-ov=TOKEN` (a browser) or
  `Authorization: Bearer TOKEN` (the CPRS relay and other non-browser
  clients). Both are headers Caddy's access log redacts by default; Janus
  accepts the token in no other place. A request carrying both, or two
  different tokens, is 400.
- `__Host-ov` is stripped from every request the site forwards anywhere
  else (an upstream, the hub bridge, files), as the auth wall strips its
  own cookie: the cookie's `Path=/` is required by the `__Host-` prefix,
  so the browser sends it to every path on the host.

**One at a time, in order.** A session runs one request at a time. A
request that arrives while one runs waits in the session's queue (FIFO,
depth `queue`); one more is 503. A waiting request whose client goes away
leaves the queue and is never sent. A running request whose client goes
away is still read to its reply's end and the reply discarded, so the
stream stays aligned for the session's next request; the `rpc_timeout`
and `max_reply` bounds still apply.

**Reading a reply** (`protocol xwb`, RPC-HTTPS §3): a short string, a
short string, then data to `\x04`, then one more `\x04` when the data's
first byte is `\x18`. Janus reads by this rule and never by waiting for
the stream to pause. The reply streams to the client as it is read:
response headers go out with the first reply byte, and the body follows
in the order read, flushed per read, never held whole.

**Ending.** A session ends when:

| Cause | `OV-Session-Ended` |
| --- | --- |
| a `#BYE#` reply (`\0\0#BYE#\x04`) completes; Janus closes the stream and answers that reply with `Set-Cookie: __Host-ov=; Max-Age=0; …` | `bye` |
| the stream closes or errors while idle (the backend's idle timeout, or the process ended) | `closed` |
| not signed on within `signon_timeout` | `signon-timeout` |
| a request passes `rpc_timeout` | `rpc-timeout` |
| a reply passes `max_reply` | `reply-too-large` |
| the backend ends the stream mid-reply | `closed` |
| a committed reload removes the route (below) | `route-removed` |
| the process restarts | none: the token is unknown (`unknown`) |

Janus notices an idle stream's close at once: one reader goroutine per
session owns every read of the stream, so between requests it is blocked
reading, and EOF or an error there ends the session and drops its entry.
Bytes that arrive while no request runs are a protocol violation: the
session ends (`closed`) and one warn line names the route.

An ended session's token is remembered as a tombstone for 10 minutes
(bounded at the route's `max_sessions` × 4 entries, oldest dropped
first), so its next request learns why: `401` with `OV-Session-Ended`
naming the cause. A token Janus never saw, or whose tombstone has gone,
is `401` with `OV-Session-Ended: unknown`.

## Sign-on (`protocol xwb`)

The one fact Janus reads from the protocol: a session is **signed on**
once the reply to an `XUS AV CODE` request has a first data line (the
bytes after the two short strings, up to `\r\n` or the end byte) that is
a decimal integer above 0, VistA's DUZ. The same RPC carries the access
and verify codes, the handle, and the CCOW sign-ons, so this covers them
all. Janus reads only the RPC's name from the request's chunk 2 and that
one line of the reply, as the reply streams past; it never logs, stores,
or exposes either, and a signed-on session keeps no DUZ.

A session not signed on within `signon_timeout` of its `TCPConnect` is
ended: its stream is closed, so em exits. With `max_unsigned` and
`per_client_unsigned`, this bounds what a client that never signs on can
hold: a few processes, for a minute.

## The stream (`protocol xwb`)

On a new session Janus dials the target (3 s connect limit) and writes,
first and once, a PROXY protocol version 1 line:

```
PROXY TCP4 <client> <server> <client-port> <server-port>\r\n
```

`TCP6` for IPv6 addresses. `<server>` and `<server-port>` are the HTTPS
connection's local address. `<client>` and `<client-port>` are the TCP
peer of the HTTPS connection, unless Caddy's `trusted_proxies` trusts that
peer, when they are Caddy's client IP (`client_ip`) and port 0; never a
header from an untrusted peer. The backend makes this the session's
address (Kernel's sign-on log and failed-sign-on lockout key on it), so it
is the same address Janus's own per-client caps use.

Then the `TCPConnect` body, and for every later request its body,
unchanged. A write error, or a dial error, before any reply byte is `502`
and ends the session.

## Admission

Every request to a route's path is judged in this order, first match
wins. The checks run in the site handler before path validation and the
data plane, after the identity-header strip, the `wan` local-name refusal,
and `/ping`.

| # | Condition | Answer |
| --- | --- | --- |
| 1 | Method is not `POST` | 405 with `Allow: POST` |
| 2 | The request arrived in TLS early data (`r.TLS == nil` or `!r.TLS.HandshakeComplete`) | 425 Too Early |
| 3 | `Origin` present and not allowed by the route's policy, or the token came as a cookie or an `Origin` is present and `X-OV: 1` is absent | 403, logged with the reason and Origin |
| 4 | `Content-Type` is not `application/x-xwb` | 415 |
| 5 | Body exceeds `max_request`, or is not exactly one message: does not start with `[XWB]`, its fourth header digit is not `0` (the backend sends no reply, so the client would hang), its structure does not walk to its end byte (RPC-HTTPS §3, the walker VistA's parser runs), or bytes follow the end | 400; the body is read only to the limit |
| 6 | Two tokens, or a malformed one | 400 |
| 7 | No token, and the message is not `TCPConnect` | 401, `OV-Session-Ended: unknown` |
| 8 | A token that names no live session | 401 with its tombstone's cause, or `unknown` |
| 9 | No token, `TCPConnect`: the route's or the process's session count, the route's unsigned count, or this client's session or unsigned count is at its cap | 503 with `Retry-After: 5`, logged with which cap |
| 10 | No token, `TCPConnect`: the target cannot be dialed | 502, logged with the error; the slot is released |
| 11 | A live session whose queue is full | 503 with `Retry-After: 1` |
| 12 | Otherwise | the request joins its session's queue, then runs |

Row 3 is the browser rule: a browser sends `Origin` on every `POST` and the
cookie on its own; `X-OV: 1` is a header no page elsewhere can attach
without a CORS preflight, which the route never answers. A non-browser
client presenting `Authorization: Bearer` sends no `Origin` and needs no
`X-OV`. The cap reservation (row 9) is atomic, so racing `TCPConnect`s
cannot both pass a cap.

Running a request:

| Outcome | Answer |
| --- | --- |
| The reply ends by the framing rule | 200 and the reply; a `#BYE#` reply ends the session |
| `rpc_timeout` passes before the first reply byte | 504, `OV-Session-Ended: rpc-timeout`; the session ends (its stream may be mid-reply) |
| `rpc_timeout` or `max_reply` passes after the first byte | the response is aborted (HTTP/2 `RST_STREAM`, HTTP/1.1 connection closed), since its 200 is already sent; the session ends |
| The stream closes before the first reply byte | 502, `OV-Session-Ended: closed` |
| The stream closes mid-reply | the response is aborted; the session ends |

Janus never retries a request: an RPC may have changed data.

## Auth gates

A route is **exempt** from the site's `auth` gates by default: VistA's
sign-on is the authentication, and the CPRS relay cannot sign on to Janus.
A gate whose prefix names the route's path exactly (`gate /rpc { … }` for
route `/rpc`) is the explicit opt-in and applies to it: a web-only site
behind Janus's wall keeps `/rpc` behind it. A broader gate (`gate /`)
never covers a route. The exemption is printed at provision, once per
route, at info: "rpc /rpc on vista.example.org is not behind gate /; VistA
authenticates its sessions".

Identity headers (`Remote-User`, `Rip-Site`, every spelling) are stripped
before admission, as on every Janus site; `rpc` injects none.

## Lifecycle across reloads

Sessions live in pooled process state (`janusState.rpc`), so a reload
keeps them. Routes follow the stage-and-commit model (`stageReconciliation`,
`commitReconciliation`): nothing a generation stages reaches requests
until it commits.

- **Identical reload.** No session is touched.
- **A route's limits change.** New limits apply to new admissions and new
  requests at commit; a running request keeps its timeout; sessions over a
  lowered cap are not ended.
- **A route's target or protocol changes.** Existing sessions keep their
  streams (a stream does not depend on the configuration that opened it);
  new sessions use the new target.
- **A route is removed.** At commit its sessions end (`route-removed`)
  and their streams close; em logs each user out.
- **Aborted reload.** Nothing staged went live; nothing to undo.
- **Restart.** Every stream closes with the process, every em exits, and
  every token is unknown.

## Hard errors

Parse time:

- `rpc` in the global `janus` block.
- A route without a path and target; a path not absolute or repeated
  within the site.
- A target whose network is not `unix`, whose path is not absolute and
  clean, or that carries a port.
- An unknown option, a repeated option, a value outside its range,
  `protocol` other than `xwb`, `per_client` above `max_sessions`,
  `per_client_unsigned` above `max_unsigned`, or `max_unsigned` above
  `max_sessions`.
- `origin any`, an empty `origin`, or a non-hostname token.

Start time:

- A route on a wildcard or catch-all site.
- A route's path equal to the site's hub path, a webtransport route's
  path, or `/ping`.

## Control and observability

`GET /1.0/rpc` on every control listener answers `{"routes":{}}` with no
routes, otherwise:

```json
{
  "sessions": 3,
  "routes": {
    "vista.example.org/rpc": {
      "target": "unix//run/openvista/xwb.sock",
      "protocol": "xwb",
      "sessions": 3,
      "unsigned": 1,
      "max_sessions": 256,
      "max_unsigned": 16,
      "started": 41,
      "signed_on": 37,
      "requests": 18402,
      "bytes_in": 2209811,
      "bytes_out": 90112044,
      "ended": {"bye": 30, "closed": 6, "signon_timeout": 1, "rpc_timeout": 0, "reply_too_large": 0, "route_removed": 0},
      "refused": {"method": 0, "early_data": 0, "origin": 2, "content_type": 0, "message": 1, "token": 0, "unknown": 4, "cap": 0, "dial": 0, "queue": 0}
    }
  }
}
```

Counters are monotonic for the process and survive reloads. No token,
session id, client address, or user appears on this surface.

Logs (at most these; never a body, token, RPC name, or reply line):

- Each session's start and end at info: route, a session id (16 random
  hex characters, unrelated to the token), the client address, the end's
  cause, its duration, requests, and bytes each way.
- Each request at debug: route, session id, duration, status, and bytes.
  (Info would put one line per RPC in the process log; the access log
  already records each request.)
- Each refusal at warn with its row, never the body.

The access log (capability 9) records `/rpc` requests like any other; its
`Cookie` and `Authorization` fields read `REDACTED` (Caddy's default) and
the response's `Set-Cookie` likewise. A server with `log_credentials`
enabled would log tokens; Start refuses a route on such a server.

## Non-goals (v1)

- Any protocol but `xwb`; streams to TCP targets; a target chosen per
  request or registered hot through `/1.0`.
- Retries, request replay, and resuming a session on another stream.
- Push to the client: a web client uses the hub (RPC-HTTPS §1).
- Session listing, inspection, or revocation over `/1.0`.
- Mutual TLS for relays; a later option.
- HTTP/3: the seed keeps it off; where an operator enables it, the
  early-data refusal (row 2) holds.

## Decisions

| # | Decision | Ruling |
| --- | --- | --- |
| 1 | Name | `rpc`, with `protocol xwb` its first framing rule |
| 2 | Sign-on detection | The `XUS AV CODE` reply's first line above 0, plus `signon_timeout` (60 s) |
| 3 | PROXY client | TCP peer, or Caddy's client IP when `trusted_proxies` trusts the peer |
| 4 | Auth gates | Exempt by default; an exact-path gate opts in |
| 5 | Limits | `rpc_timeout` 10 m, `queue` 8, `max_request` 1 MiB, `max_reply` 64 MiB streamed |
| 6 | Token transport | `Set-Cookie` on the `TCPConnect` reply only; requests by `Cookie` or `Authorization: Bearer`, both redacted by Caddy's logs |
| 7 | Idle | No Janus timer; the stream's close is noticed at once |

## Acceptance

Go tests (`go test ./...`), with a **fake em**: a test helper that accepts
on a Unix socket, requires the PROXY line first, then answers each message
it walks with a scripted reply, and records what it received. Its fixtures
are RPC-HTTPS §3's measured replies, byte for byte (`accept`, `XWB IM
HERE`, `XWB GET BROKER INFO`, `XUS SIGNON SETUP`, `XUS AV CODE` with DUZ
`100` and with `0`, a security refusal, an M error with its second `\x04`,
`#BYE#`).

- Parse: every legal form; every parse-time hard error with its message.
- The message walker: RPC-HTTPS §3's examples; a value holding `\x04`;
  list continuation (`t`); 9-digit widths; a fourth header digit not `0`;
  bytes after the end; truncated messages. Plus a fuzz target asserting
  the walker never accepts a body that does not end at its end byte.
- The reply reader: each §3 fixture; an M error's second `\x04`; a reply
  split across many reads; a reply at and over `max_reply`.
- Admission: every row above, in order.
- Sessions: `TCPConnect` mints a token on `Set-Cookie` only; Cookie and
  Bearer both work; FIFO order under concurrent requests; the queue cap;
  a client gone while queued (never sent) and while running (reply
  drained, next request aligned); `#BYE#`; idle close noticed without a
  request; unsolicited bytes; every `OV-Session-Ended` cause; tombstone
  expiry.
- Sign-on: DUZ > 0 marks signed on; DUZ 0 does not; `signon_timeout`
  closes an unsigned session and frees its slot; the unsigned caps.
- PROXY line: TCP4 and TCP6; the TCP peer; Caddy's client IP behind a
  trusted proxy; an untrusted `X-Forwarded-For` ignored.
- Timeouts: `rpc_timeout` before the first byte (504) and after it
  (aborted response).
- Auth: exempt under `gate /`; covered by an exact `gate /rpc`.
- `__Host-ov` stripped from a request forwarded to an upstream.
- Reload: limits change; target change keeps sessions; removal ends them.
- No token, body, RPC name, or reply line in any log line (an observer
  test over every path above).

`./test.sh` group `rpc` (after webtransport), with the testkit's fake em
on a Unix socket:

- `TCPConnect` → 200, `accept`, a `__Host-ov` cookie; `XWB IM HERE` with
  the cookie and `X-OV: 1` → 200; the same with Bearer and no `X-OV` → 200.
- An M-error reply arrives whole with its second `\x04`.
- A cross-origin `POST`, and a cookie without `X-OV`, → 403.
- A body not `[XWB]`, and one with a fourth digit `1`, → 400 at once (the
  request does not hang).
- No token and not `TCPConnect` → 401; after `#BYE#` → 401 `bye`.
- The fake em closing an idle session → the next request is 401 `closed`.
- The unsigned cap → 503; `signon_timeout` (set to 10 s) frees it.
- The access log holds no token: grep for the minted token finds nothing.

End to end against real em (Em provides the environment): the CPRS relay
signs on through Janus to VistA, as `test/relay`'s mini-Janus does today.
